## 1. R1：你指出的两处问题都成立，已修复

### 1.1 后端版本失配没有取消推荐资格

**原状**：版本不符只写进 `limitations`，`recommended()` 仍可能选中它。

**修复**：

* 每个候选保存**自己**的 `backend` / `backend_version`（扫描器 CSV 本来就有这两列，
  之前被一个全局身份覆盖了 —— 多后端一起搜时，不同版本的结果会共享同一个身份）；
* 身份检查并入 `check_comparability`：后端缺失、版本缺失、版本不同 → 不可比较；
* 原生回放的**槽位别名必须解析成实际版本**：装了工具时读它自带的
  `query_versions.yaml`，否则用配置里的 `backend_version_aliases`；
  **解析不出来就不算身份匹配**（`current` 本身不是版本号）。
  实测解析结果：`vllm.current = 0.24.0`、`trtllm.current = 1.3.0rc20`；
* 顺带纠正：`replicas` 不再被当成 DP（原先把 `parallelism.replicas` 写进了 `dp_size`）。

**一个可复核的副产物**：这解释了上一轮"support 报 trtllm 1.3.0rc23、扫描器却加载
1.3.0rc20"的差异 —— 前者是 `next` 槽位（由更新的声明版本推导），后者是 `current`。
两个都是真实条目，但不是同一个身份，所以必须按候选记录实际版本。

### 1.2 `recommended()` 没有纳入资源与预算

**原状**：只按"预测达标 + 最大吞吐"选，GPU 总量、拓扑完整性、Sizing 可行性、预算都没参与。

**修复**：

* 新增 `PlanRequest.max_total_gpus`（可选）。**未给出时不做任何假设**：
  不取 `server_id` 的卡数，也不把"没给上限"当成"不超限"；
* 用**现有 Sizing** 校验每个候选：以该候选的 TP/DP 重新调用
  `plan_deployment_for`，取静态结论与卡数；工具报的卡数与 Sizing 口径不一致 → 不可推荐；
* PP>1 / EP / PD 分离 / CP 等本系统不建模的拓扑 → `resource_feasible=False`，
  只作模拟参考，**不宣称可部署**；
* 预算复用既有的 `check_budget`：成本不完整 / 币种未确认 / 金额缺失一律 `unknown`，
  不得读成"没超预算"；
* 新增 `eligible()` 作为**正式推荐池**（身份明确 + 资源可行 + P99 完整 + 不超预算），
  `recommended()` / `best_effort()` 只在池内取；
* 报告措辞：没有达标候选时标题改为「**未达标参考配置（模拟）**」，
  不再称"推荐配置"；池子为空时明确写「无符合条件的模拟候选」并逐条列出门槛原因。

### 1.3 验收反例（15 条，全部通过）

| 反例 | 结果 |
|---|---|
| 后端版本不符（要求 0.25.0，模拟 0.24.0） | 不可比较，不进池 |
| 槽位别名无法解析（`current` 无别名表） | 不可比较，不进池 |
| GPU 超额（上限 4，候选 8 卡） | `within_gpu_budget=False`，不进池 |
| 静态不可行（可用显存压到 5%） | `resource_feasible=False` |
| 卡数口径不一致（工具 4 卡 / Sizing 8 卡） | 不可推荐 |
| PP>1 / PD 分离 | 只作参考，明确"不宣称可部署" |
| 缺 TP | 无法校验 → 不可推荐 |
| 工作点不一致（并发不同） | 不可比较 |
| 多后端结果 | 每行保留自己的 backend/version |
| `replicas` | 不再覆盖 `dp_size` |

## 2. R2：自动搜索 → 原生 P99 回放（本轮核心）

### 2.1 用户只填一份需求 YAML

`data/examples/scenario_simulation_auto.example.yaml`。系统按需求自动生成：

* 扫描器的 exp YAML（模型/精度、system、ISL/OSL、并发、后端+版本、
  搜索空间受 `max_total_gpus` 约束）；
  **SLA 边界刻意设到极松** —— 工具自带的过滤是聚合均值口径，我们不用它筛；
* 每个入选候选的原生回放 YAML（`engine.workers.aggregated.parallelism` + `traffic`）。

### 2.2 两段式流程（实测跑通）

```
需求 → 自动生成搜索输入 → 扫描器 → 身份/资源过滤 → Top-N(≤3)
     → 自动生成 predict 输入 → 原生回放 → 关联回搜索工作点 → 模拟推荐
```

实测（Qwen3-32B bf16 / h100_sxm / vllm 0.24.0 / 8K-256 / 并发 32 / 上限 8 卡 / Top-2）：

* 搜索 36 个 Pareto 点 → 过滤后取 Top-2 → 1 条完成回放（另一条静态不可行，按规则不入选）；
* 回放结果自动关联：`linked_search_candidate_id = sim-sweeper:...tp4...-c32-ctx8192`，
  并在报告里写明"回放的工作点来自搜索结果 …（ctx_tokens=8192、并发=32）"；
* 每次运行都落盘 `manifest.json`：输入/输出文件的 **sha256**、工具版本、
  后端版本、搜索规格、失败项；
* 单候选失败只记录到 `manifest.errors`，不影响其它候选；
* 未装工具时**跳过**（验证链打印"跳过：未找到 AISimulate 独立环境"），
  离线 Demo 仍可读归档复现。

### 2.3 对齐规则（"无法对齐只能分别展示"）

原生回放只对**同一个部署 + 同一个工作点**的候选执行，否则只作参考：

| 条件 | 处理 |
|---|---|
| `DP ≠ 1` | 原生配置无法表达 data parallel → 不对齐 |
| `ctx_tokens ≠ ISL` | 每步上下文预算不同（整段 prefill vs 分批）→ 不对齐 |
| 后端/版本缺失或不一致 | 无法保证同一份性能数据 → 不对齐 |
| 缺 TP | 无法构造回放配置 |

对齐不上的候选不会消失：它们留在结果里并带 `link_reasons`，
报告按"搜索口径"与"回放口径"分别展示。

### 2.4 与 TCO / 预算联动

* 预算已明确且成本完整 → 超预算候选不进推荐池（`exceeds_budget`）；
* 币种/成本口径/年限不一致，或成本不完整 → **不排序**，报告明确写
  「成本排序不可用：…，以下按吞吐给出，且**不得**称为成本最优」；
* 多候选满足时，报告第一行就写明排序目标（吞吐优先 / 成本优先），
  不提供含糊的"全局最优"。

## 4. 现在能做到什么、仍然不能做什么

**能**（一份 YAML 跑完）：

给定模型 + GPU（含可用卡数上限）+ 负载 + P99 SLA + 预算 → 自动搜索部署配置 →
资源与静态可行性过滤 → 对少数候选回放 P99 → 与成本/预算比较 → 输出方案文档，
并明确标注每个数字属于实测 / 公开参考 / 模拟预测 / 假设成本。

**不能**（保持如实标注）：

1. 模拟**仍不是实测**：`predicted_pass` 永远不等于 `observed_pass`；
   模拟值不写 `BenchmarkRun` / `CapacityPoint`。
2. 官方精度快照里**没有 Qwen3-32B**，全量 MAPE 是 TTFT 45.27% / TPOT 22.39% ——
   模拟值只适合排序与发现明显不可行，不能当作可承诺时延。
3. 扫描器的单点 ≈ 原生回放的中位数（不是 P99，P99 可达其 13.9 倍）；
   达标与否一律由我们用 P99 判。
4. PP / EP / PD 分离等拓扑本系统不建模，模拟结果只作参考。
5. 生产自动报价仍禁用；Public 仓库历史定价数据风险仍需独立闭环
   （未经授权不改写 Git 历史）。

## 6. 复审后的 V7.0 最终加固（F1–F5）

### F1（P0）成本排序的错误选择与潜在异常

**原状**：`cost_ranking_available()` 只要求池里**存在**一条完整成本；
`recommended("cost")` 却对**所有**达标候选取 `total_cash_over_horizon` 最小值 ——
混入 `None` 会直接抛异常，也可能把缺成本者当成"最便宜"。
另外成本不可用时 `recommended` 返回 `None`，报告退回 `best_effort()`，
可能选中**预测不达标**但吞吐更高的候选。

**修复**：
* 成本排序要求**所有参与排序的达标候选**都有可比成本（完整、金额已知、
  且币种/口径/年限一致），否则 `available=False` 并给出具体原因；
* `recommended("cost")` 在不可用时**降级为吞吐优先，但仍在预测达标的候选里选**，
  不再返回 `None`、也不会落到 `best_effort`；
* 报告明确写"**已降级为吞吐优先**（仍然只从预测达标的候选里选）"。
* 反向测试 5 条：部分缺成本、双候选成本可比、币种混用、不降级到失败候选、报告措辞。

### F2（P0）单个回放超时可能中断整轮

**原状**：`run_two_stage` 只捕获 `SimulationNotAvailable`，
`subprocess.TimeoutExpired` 会直接冒泡。

**修复**：
* `run_external` 把 `TimeoutExpired` / `OSError` 转成受控的 `SimulationNotAvailable`
  （消息里写明"执行超时"或"无法启动"）；
* 逐候选回放抽成 `_replay_one()`，调用处用 `except Exception` 兜住**任何**失败
  （超时、启动失败、输出缺失、JSON 损坏、解析异常），只写 `manifest.errors` 并继续；
* 搜索阶段同样兜住超时/启动失败，返回可解释的 error；
* `external_tool_available()` 的探测也加了超时保护。
* 反向测试 3 条：第一条超时、第二条成功；超时被转成受控异常；资格回调自身异常也不中断。

### F3（P1）Top-N 名额可能被不可对齐候选占用

**原状**：先按吞吐取 Top-N，再检查能否对齐 —— 吞吐最高但 `ctx_tokens` 不一致的
候选会白占名额。

**修复**：顺序改为 **资格过滤 → 对齐检查 → 排序 → 取 Top-N**。
不可对齐的候选仍保留在结果里并带 `link_reasons`，只是不占用回放名额。
反向测试：三条候选（最高不可对齐、次高可对齐、最低），`top_n=1` 时必须回放次高者，
且最高那条出现在报告的未对齐清单里。

### F4（P1）搜索并发约束与可重复运行

**核实结果**：AISimulate 的 exp 搜索空间**没有"请求并发"这个约束维度** ——
`decode_max_batch_size` 实际是 **decode 步的 token 预算**
（代码里写作 `decode_max_num_tokens`），不是请求数。
扫描器会枚举并发并输出多行，因此：

* **搜索约束**：GPU 数、TP/PP/DP/MoE/CP、后端与版本、ISL/OSL、数据库模式；
* **结果过滤**：目标并发由我们在解析后筛选（`check_comparability` 的并发比对）。

这两者已在代码注释与报告中区分，并有测试固定住"搜索配置里不含并发字段"这一事实，
避免以后误以为"搜索是按并发 32 优化的"。可重复性由 SILICON 模式保证
（同一命令两次结果表逐字相同，PoC §3.4 已实测），
自动模式每次运行都把输入/输出与 sha256 写入 `manifest.json`。
